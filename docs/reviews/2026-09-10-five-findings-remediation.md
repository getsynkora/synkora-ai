# Remediation of the five project security findings

All five findings in [the project review](2026-09-10-project-security-review.md) are addressed in the current working tree. This document describes implementation and local validation; it does not imply deployment.

## Changes

| Finding | Implemented protection |
| --- | --- |
| SR-01: Okta configuration authorization | All four configuration endpoints require current ADMIN/OWNER authority. Domains cannot contain URL credentials, paths or ports; issuer URLs must use HTTPS on the configured domain. Changing provider identity requires a replacement secret before any mutation. Login state is consumed atomically and tied to a configuration fingerprint, so a callback cannot use changed settings. OIDC HTTP calls use bounded, DNS-pinned public connections without redirects. |
| SR-02: Monitoring SSRF | Connection tests and background metrics exports use the same bounded, DNS-pinned transport. Public destinations remain supported. Private access requires an operator-owned tenant/origin policy. Redirects are not followed, error bodies are not exposed, and webhook tests/exports permit only POST, PUT and PATCH. IPv4 and IPv6 cloud metadata destinations remain blocked even with private approval. |
| SR-03: Widget/session CORS | Widget CORS is restricted to explicit public widget routes and does not allow ambient cookies. Widget keys cannot grant CORS access to session or widget-management routes. Dashboard matching includes scheme, hostname and effective port. Cookie refresh independently requires an approved dashboard Origin; mobile/body-token refresh continues to work without browser cookies. Empty dashboard origin configuration denies cross-origin access. |
| SR-04: Report download signing | Tokens use validated application settings, including dotenv-loaded keys, and fail closed on missing keys. Tokens bind purpose, timestamp, tenant and a canonical report storage key. Downloads require current tenant membership; foreign keys, legacy tokens, future/expired tokens, traversal and local symlinks are rejected. Local downloads resolve under configured storage instead of arbitrary `/tmp` paths. S3 redirects are generated only after tenant authorization, with a 60-second URL lifetime. |
| SR-05: OpenAPI DNS rebinding | Imports use the existing bounded public-fetch transport, with connection-time DNS validation and literal-IP pinning. Every redirect is rechecked, HTTPS downgrade is denied, and responses are limited to 5 MiB. |

The report export service previously called a storage method that its configured wrapper did not implement, and returned download links with the wrong route prefix. The fix uses the existing storage save API, unique tenant-scoped keys, and the correct route. Real CSV, JSON, Excel and HTML export/download round trips are covered. Filenames cannot select directories; HTML report titles are escaped.

## Operator and client compatibility

- Deploy the API and worker changes together. This work does not require a new database migration.
- Set `CORS_ORIGINS` to the actual dashboard origins, including nondefault ports. Cookie refresh callers must send the browser's Origin; native clients can continue supplying their refresh token in the body without cookies. Arbitrary extension origins do not receive credentialed CORS permission.
- Old report download tokens must be regenerated by exporting again. Current download requests require the tenant's bearer session. Existing stored report objects are not deleted.
- Changing an Okta domain, issuer, client ID or authorization-server ID requires a replacement secret. In-flight SSO attempts using an old or changed configuration must restart login.
- Monitoring webhooks configured with GET/DELETE or redirects need a direct POST/PUT/PATCH destination. Other provider-specific health checks retain their required GET/OPTIONS methods.
- Private monitoring is denied by default. If required, configure `MONITORING_ALLOWED_PRIVATE_ORIGINS` on **both API and worker deployments**, using the tenant UUID and exact approved origins:

```dotenv
MONITORING_ALLOWED_PRIVATE_ORIGINS={"11111111-1111-4111-8111-111111111111":["https://metrics.internal:8443"]}
```

This deployment setting is not writable through integration configuration. Approval is limited to the listed tenant, scheme, hostname and port; it does not inherit `MCP_ALLOWED_PRIVATE_HOSTS`. Operators should approve only monitoring services intended for that tenant. Public monitoring destinations need no entry. The response limit is 1 MiB for monitoring/OIDC requests, with explicit timeouts.

## Validation

The new regression suites are:

- `api/tests/unit/services/security/test_review_identity_boundaries.py`
- `api/tests/unit/services/security/test_review_http_boundaries.py`
- `api/tests/unit/services/security/test_review_report_downloads.py`

They contain **62 passing tests** covering real ASGI route authorization, allowed refresh flows, blocked widget/session requests, pinned transport behavior with synthetic DNS/HTTP peers, private-origin policy isolation, background exporter dispatch, real local report round trips, and S3 authorization before presigning.

Existing SSO unit tests now mock the checked-request boundary. Existing export controller fixtures use tenant-scoped keys. The broader final command also covers existing authentication, widget, OAuth, storage, SCIM, webhook, controller-remediation and MCP transport regressions. Results are recorded in `2026-09-10-five-findings-validation.json`.


Four unchanged private-Redis quota tests are excluded from this command; they passed during the preceding review with socket access. Ruff and whitespace checks pass for this change. Existing native SAML test stubs mean these tests do not certify live IdP interoperability. No live external service, production deployment or browser exploit was used. Frontend code and dependency locks were not changed by this remediation.
